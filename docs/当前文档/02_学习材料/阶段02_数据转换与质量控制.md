## 1. 面试时先用这一段概括

如果面试官问“你的量化项目如何做数据处理”，可以先用下面这段 60～90 秒回答：

> 我的数据层分为原始层、标准化层和访问层。原始层保留 Tushare 返回的 CSV，尽量不修改，作为可追溯证据；标准化层按数据语义完成日期解析、字段类型统一、主键去重、复权、单位换算、PIT 版本保留、状态展开，并写成 Parquet；访问层通过统一 loader 按日期和股票过滤，大表使用 Parquet 谓词下推，小型 PIT 表缓存后按调仓日做 as-of 查询。质量检查不只看空值，还检查粒度、主键、时间覆盖、跨表键覆盖、公式一致性、PIT 可见性和截面覆盖。对这个项目而言，最关键的是后复权收益、全收益基准、自由流通市值、财务公告日和历史成分股生效日。当前实现的主要不足是自动化 quality gate 尚未接入流水线，部分转换先写文件后验证，而且行业和 ST 历史覆盖仍有缺口，因此我不会把“代码能跑”表述为“数据已经生产可用”。

这段回答包含了业界最关心的五件事：

1. 分层；
2. 粒度与主键；
3. 时间可用性；
4. 质量门禁；
5. 对缺陷和风险的诚实判断。

不要只回答“我做了去重、缺失值处理和标准化”。这类回答没有说明数据为何在某个时点可用，也没有说明怎样阻止错误数据进入模型。

## 2. 数据处理真正要解决什么

量化数据处理不是把 CSV 换成 Parquet。它要建立一份下游可以依赖的数据契约：

```text
一个数值是谁的？          ts_code
它描述哪个时点或期间？    trade_date / end_date
市场什么时候知道它？      pit_date / ann_date
它采用什么单位和口径？    元、万元、股、万股、百分比、小数
一行代表什么？            日行情、财报版本、事件、调仓截面
主键是什么？              哪些列的组合必须唯一
缺失代表什么？            无事件、未披露、下载失败、无法交易
它能否用于 T 日决策？      是否满足 point-in-time
出现异常时怎样处理？      阻断、隔离、降级还是告警
```

因此，完整的数据处理应拆成三层：

| 层次 | 本项目位置 | 职责 | 不应承担的职责 |
|---|---|---|---|
| Raw 原始层 | `data/raw/` | 保存供应商原始响应和下载元数据 | 不在这里做因子计算 |
| Processed 标准层 | `data/processed/*.parquet` | 类型、粒度、口径、时间、主键、状态标准化 | 不应根据未来回测效果改数据 |
| Access 访问层 | `src/data/loader.py`、`pit_loader.py` | 日期切片、PIT 快照、缓存、统一接口 | 不应默默修补上游错误 |

项目当前已经有这三层的形状，但 Raw 层 manifest、Processed 层原子发布、自动 quality gate 尚未闭环。

## 3. 先掌握“粒度”，再看任何代码

### 3.1 什么是粒度

粒度是“一行数据代表什么”。不先确认粒度，去重和 join 都可能做错。

例如：

- 日行情的一行是“一只股票在一个交易日的行情”；
- 财务 PIT 表的一行是“一只股票、一个报告期、一次可见版本”；
- 分红表的一行是“一次分红事件”；
- 成分股表的一行是“一个调仓截面中的一只成分股”。

### 3.2 本项目核心表契约

| 模块 | 文件 | 一行代表什么 | 应有主键 | 核心日期 |
|---|---|---|---|---|
| M1 | `daily_quote.parquet` | 股票日行情 | `(trade_date, ts_code)` | `trade_date` |
| M2 | `daily_basic.parquet` | 股票日度估值和股本 | `(trade_date, ts_code)` | `trade_date` |
| M3 | `index_quote.parquet` | 指数日行情 | `trade_date` | `trade_date` |
| M4 | `industry.parquet` | 股票当日行业归属 | `(trade_date, ts_code)` | `trade_date`，源表含 `in_date/out_date` |
| M5 | `financial_pit.parquet` | 财报期在某次披露后的版本 | `(pit_date, ts_code, end_date)` | `pit_date`、`end_date` |
| M6 | `indicator_pit.parquet` | 财务指标的披露版本 | `(pit_date, ts_code, end_date)` | `pit_date`、`end_date` |
| M7 | `holder_pit.parquet` | 股东人数的一次可见版本 | `(pit_date, ts_code, end_date)` | `available_date`、`pit_date`、`end_date` |
| M8 | `dividend_pit.parquet` | 一次分红事件 | `(pit_date, ts_code, event_id)` | `pit_date`、`ex_date`、`end_date` |
| M9 | `margin.parquet` | 股票日度融资融券 | `(trade_date, ts_code)` | `trade_date` |
| M10 | `moneyflow.parquet` | 股票日度资金流 | `(trade_date, ts_code)` | `trade_date` |
| M11 | `stock_status.parquet` | 股票当日交易状态 | `(trade_date, ts_code)` | `trade_date` |
| M12 | `index_member.parquet` | 月度成分股截面中的股票 | `(rebalance_date, ts_code)` | `rebalance_date` |

面试高频追问：“为什么财务表不能只用 `(ts_code, end_date)`？”

标准回答：同一报告期可能先披露初版，之后再修订。如果只保留最终版本，历史回测会让修订前的 T 日看到未来才出现的最终值。必须保存版本维度，查询 T 日时先过滤 `pit_date <= T`，再选择当时可见的最新版本。

## 5. 通用转换函数逐个理解

### 5.1 `_parse_yyyymmdd()`：日期标准化

当前代码：

```python
pd.to_datetime(series.astype(str).str[:8], format="%Y%m%d", errors="coerce")
```

它解决三个问题：

- 原始日期可能是整数或字符串；
- 截取前 8 位规避附加字符；
- 非法日期转为 `NaT`，而不是让整个批次立即报错。

但 `errors="coerce"` 只完成容错，不等于质量合格。业界实现必须随后检查：

```text
NaT 数量和比例
NaT 出现在哪些源文件、股票和字段
关键日期是否允许 NaT
日期是否超出请求区间
是否出现未来日期
```

面试回答：“为什么统一用 `pd.Timestamp`？”

因为字符串比较依赖格式，容易出现时区、边界和字典序问题；统一时间类型后才能可靠进行区间过滤、as-of、窗口和 Parquet predicate pushdown。

### 5.2 `_read_csv_safe()`：目前过于宽松

该函数把空文件返回为 `None`，也把编码、schema、I/O 等其他异常记录 warning 后返回 `None`。随后 `_load_csv_dir()`继续拼接其他文件。

优点：单个稀疏事件文件为空时不会使批处理崩溃。

问题：核心行情文件损坏时也可能被静默跳过，最终得到一个不完整但能写出的数据集。

业界应按数据类型分类：

| 情况 | 核心行情/财务 | 稀疏事件数据 |
|---|---|---|
| 合法无记录 | 需由 manifest 明确证明 | 可接受并记录 `legitimate_empty` |
| schema 缺列 | 立即失败 | 立即失败 |
| 编码/解析失败 | 立即失败 | 隔离并阻断该模块 |
| API 失败产生空文件 | 立即失败 | 立即失败 |

这叫 **fail closed**：无法证明正确时不允许继续进入下游。

### 5.3 `_load_csv_dir()`：并行读取与纵向拼接

函数使用 `ThreadPoolExecutor`并发读取文件，最后 `pd.concat(..., ignore_index=True)`。

适用原因：大量小 CSV 的主要成本是文件 I/O，并发可以缩短等待；`ignore_index=True`避免保留没有业务意义的原 CSV 行号。

当前限制：所有文件最终同时驻留内存，数据规模扩大后峰值内存会很高。更稳健的扩展方案是：

1. 分批读取和转换；
2. 使用 PyArrow dataset；
3. 按年份或日期分区写 Parquet；
4. 逐批维护行数、主键和校验和；
5. 最后原子发布 manifest。

### 5.4 `_filter_date_range()`：统一样本边界

当前默认范围来自 `src/config.py`：

```text
MARKET_START = 2011-01-01
MARKET_END   = 2025-12-31
```

2011 年行情作为 2012 年训练起点前的窗口缓冲。重点是日期范围来自配置，而不是散落在函数中。

仍需补充：函数签名有类型注解，但没有运行时强制检查。字符串可能在更深处才失败。公共 loader 和转换入口应显式验证 `isinstance(date, pd.Timestamp)` 或统一转换后再校验。

### 5.5 `_save_parquet()`：格式正确，发布语义不足

Parquet 的优势：

- 列式存储，读取少量列更高效；
- 保留数据类型；
- 压缩率通常优于 CSV；
- 支持 predicate pushdown；
- 适合标准化层反复读取。

当前函数直接写最终路径，而且各模块普遍是“先保存、后断言”。这带来两个风险：

1. 写入中断可能留下损坏或半成品；
2. 验证失败时，不合格文件已经位于正式路径。

业界发布顺序应为：

```text
写临时文件
  ↓
读取临时文件复核 schema / 行数 / 主键 / 公式 / 覆盖
  ↓
生成质量报告和内容哈希
  ↓
全部通过后 atomic rename 到正式路径
  ↓
更新 manifest 指向新版本
```

不要让“文件存在”成为成功标志；成功应由“状态 + 覆盖区间 + schema 版本 + 哈希 + 质量门禁”共同定义。

## 6. M1：日行情、复权价格和收益率

### 6.1 输入与步骤

输入：

- `raw/daily_quote/*.csv`
- `raw/adj_factor/*.csv`

处理过程：

1. 读取两类文件；
2. 解析 `trade_date`；
3. 过滤研究日期；
4. 删除 `vol == 0 and amount == 0` 的记录；
5. 按 `(ts_code, trade_date)` 左连接复权因子；
6. 计算后复权开收盘价；
7. 分股票按时间排序计算收益；
8. 转为 `float64`；
9. 设 MultiIndex 并写 Parquet。

核心公式：

```python
close_adj = close * adj_factor
open_adj  = open  * adj_factor
ret       = close_adj.groupby(ts_code).pct_change()
```

### 6.2 为什么采用后复权

前复权和后复权都能在理论上构造连续收益，但项目必须全程统一。这里选后复权，是用复权因子把历史价格放到同一累计权益尺度，收益由同一条后复权价格序列计算。

关键点：原始 `pct_chg` 和 `close_adj.pct_change()`在普通交易日可能接近，但在除权除息等公司行动附近不必相等。正确验证应是：

```text
close_adj == close * adj_factor
ret == 同一股票 close_adj 的相邻期变化率
公司行动日前后抽样复算
```

当前质量 notebook 中的 `ret_equals_pct_chg_div_100` 检查与这个口径冲突，应删除或改成诊断性差异报告，不能把差异直接判成 ERROR。

### 6.3 当前代码的审计意见

- 正确：以行情为左表，不凭空生成没有行情的股票日记录。
- 正确：`pct_change(fill_method=None)`不隐式前向填充缺失价格。
- 正确：输出数值显式转为 `float64`。
- 待改：合并前后没有显式检查双方主键唯一，重复复权因子可能造成 join blow-up。
- 待核：零成交不等于“节假日误入”。也可能代表停牌或数据源特殊记录，应结合交易日历和停牌表判断并保留删除审计。
- 待改：用收益分位数是否在 ±11% 判断质量不是稳定业务规则；不同板块、上市初期和制度时期涨跌幅限制不同。

### 6.4 面试追问

**问：为什么不直接使用供应商的 `pct_chg`？**

答：策略收益口径必须和持有价格口径一致。项目使用后复权价格，因此收益由后复权价格自行计算；供应商原始涨跌幅可保留作交叉核验，但不是唯一事实源。

**问：停牌日没有价格怎么办？**

答：不能随意插值。因子窗口可以保留缺失，并设置最少有效交易日；持仓估值和交易执行需要单独的停牌规则。信号数据、估值数据和交易可执行性不能混成一个缺失值处理。

## 7. M2：自由流通市值与日度基本面

### 7.1 核心公式和单位

```python
free_float_mv = free_share * close * 10_000
log_free_float_mv = log(free_float_mv)
```

因为 `free_share` 的单位是万股，乘 `10_000` 转为股，再乘元/股，得到元。

不要混淆：

| 字段 | 含义 | 本项目用途 |
|---|---|---|
| `total_mv` | 总市值 | 描述性字段 |
| `circ_mv` | 流通市值 | 不能替代自由流通市值中性化 |
| `free_float_mv` | 自由流通股本对应市值 | 市值中性化 |

### 7.2 为什么取对数

A 股市值呈明显右偏长尾分布。直接用市值回归会让超大市值股票拥有过强杠杆；取对数后尺度更平滑，也更接近“规模暴露”的线性表达。

### 7.3 当前代码的审计意见

- 正确：单位换算写在代码和 docstring 中，可复算。
- 正确：非正市值和缺失率有检查。
- 待改：`clip(lower=1.0)`会把非正异常隐藏进对数计算；虽然之后有断言，但应该先把非法值置空/报错，再计算对数。
- 待改：先保存后断言，失败产物仍会留在正式路径。
- 待补：应检查 `daily_basic.close` 与 `daily_quote.close` 的跨表一致性和键覆盖率。

**面试问：自由流通市值缺失能否填 0？**

不能。0 会导致对数无定义，并把“未知规模”错误表示成“极小规模”。应追查数据源；仍缺失时在该截面排除该股票并报告覆盖损失。

## 8. M3：中证500全收益基准

### 8.1 当前逻辑

代码强制指数代码为 `H00905.CSI`，然后对齐股票交易日历，计算：

```python
index_ret = close.pct_change()
nav = (1 + index_ret).cumprod()
```

选择全收益指数是为了把现金分红再投资包含在基准中。若策略组合包含分红，而基准使用价格指数，超额收益会被系统性高估。

### 8.2 当前风险

指数缺日时，代码使用下一条记录的 `pre_close.bfill()`反推缺失日收盘。这是从未来记录重建过去，不适合作为 T 日可用数据。

更好的处理：

- 核心基准缺日直接阻断；
- 从同日官方备用源补齐，并记录 provenance；
- 如果仅为事后归因重建，和实时信号数据隔离，并明确标记。

**面试问：为什么股票日历和指数日历要完全对齐？**

因为超额收益必须比较同一持有区间。日历错位会让策略收益和基准收益对应不同日期，产生虚假的超额和波动。

## 9. M4：历史行业的区间连接

### 9.1 不是静态映射

股票行业会变化，所以不能拿今天的行业标签回填历史。当前逻辑对每个股票交易日选择：

```text
in_date <= trade_date < out_date_eff
```

若同时命中多条，取 `in_date` 最新的一条；找不到则标为“未分类”。这属于 slowly changing dimension 的区间连接。

### 9.2 当前审计结论

实现思想正确，但数据覆盖没有通过：2012、2013 年未分类比例约为 31.8% 和 32.2%。全样本覆盖率阈值会掩盖早期分段缺口。

此外，代码在 SW2021 文件缺失时回退到 CITICS，改变了行业定义。生产主线应直接失败，不允许只打印 warning 后改变模型语义。

质量门禁至少要按月检查：

```text
行业覆盖率
未分类比例
行业数量
新出现/消失的行业代码
同一股票同日多行业命中
行业变更日前后边界
```

**面试问：行业缺失为什么不能简单填众数？**

因为行业用于中性化和风险约束。填众数会人为赋予错误行业暴露，导致残差和行业偏离都失真。缺失过多应阻断；少量缺失也应显式隔离并报告。

## 10. M5～M8：PIT 表和事件表

### 10.1 三个时间概念

```text
end_date：财报描述到哪一期
ann_date / f_ann_date：市场何时看到
rebalance_date T：策略何时决策
```

最低可用性规则：

```text
pit_date <= T
end_date < T
```

### 10.2 为什么要保留修订版本

假设某公司 2021 年报：

```text
2022-03-20 初次披露净利润 10 亿
2022-05-10 修订为 8 亿
```

在 2022-04-30 回测截面只能看到 10 亿；在 2022-05-31 才能看到 8 亿。转换层若只保留最终 8 亿，就发生 look-ahead bias。

当前 `_dedupe_same_pit_version()`只去除同一个 `pit_date` 的重复，保留不同披露日版本，这一方向正确。另一个 `_build_pit_table()`会全局只留最终版本，但当前核心 M5～M7没有调用它；这个未使用 helper 容易误导维护者，建议删除或明确标为禁用示例。

### 10.3 财务三表宽表合并的风险

当前 M5 分别处理利润表、资产负债表、现金流量表，再仅按 `(ts_code, end_date)`外连接。三张表若修订时间不同，可能产生版本笛卡尔组合。

工业级做法：

1. 三张表分别保存原子版本；
2. 合并所有披露/修订时点形成事件时间线；
3. 每个事件时点对每张表做 backward as-of；
4. 形成“该时点市场可见”的宽表；
5. 用交错修订的合成案例做单元测试。

### 10.4 事件表不能强行变成日度快照

分红等数据可能同股同日多事件，因此需要 `event_id`。事件数据常见的两个日期用途不同：

- `pit_date`：是否已经知道该事件；
- `ex_date`：事件什么时候实际发生。

构造过去 12 个月分红时，既要满足公告可见性，也要明确按除权日还是公告日滚动，不能只按一个日期机械筛选。

## 11. M11～M12：状态矩阵和成分股快照

### 11.1 状态不是一个布尔值

项目将状态拆成停牌、ST、新股、涨停锁定、跌停锁定等字段。这是正确方向，因为：

```text
ST / 新股：通常影响能否进入投资域
停牌：已有持仓无法交易，权重应锁定
涨停：通常不能增加持仓
跌停：通常不能减少持仓
```

“不可新买”和“已有持仓必须继续持有”不能都压缩成 `tradable=False`。

### 11.2 成分股表为何是月度截面

M12将指数权重和 M11 状态合并，生成每个 `rebalance_date` 的 500 只股票。结构检查包括每期数量、权重和、状态覆盖。

但字段名 `trade_date` 不自动等于官方生效日。必须抽取正式调整公告，核对公告日、参考日和生效日，才能证明投资域是 PIT 正确的。

当前另一项阻塞是 ST 历史从 2020 年末才开始，不能证明 2012～2020 的全部训练截面正确排除了 ST 股票。

## 12. Loader：正确性与性能的边界

### 12.1 两种读取策略

`src/data/loader.py`采用：

- 大型日频表：`pd.read_parquet(..., filters=...)`做日期和股票谓词下推；
- 小型 PIT 表：整表读入模块级 `_CACHE`，然后反复做 T 日快照。

这种混合策略是合理的。大表避免每次全部加载，小表避免每个月重复 I/O。

### 12.2 谓词下推是什么

谓词下推是把日期和股票过滤传给 Parquet 引擎，让引擎尽量只读取满足条件的 row group，而不是先把全表加载进 pandas 再过滤。

要真正获得性能收益，还取决于：

- 文件是否按常用过滤键排序；
- row group 是否与日期范围大致对齐；
- 是否按年份/日期分区；
- 查询是否只选择需要的列。

当前项目写成单个大 Parquet，并未显式设计 row group 和分区，逻辑上支持过滤，但物理性能仍有优化空间。

### 12.3 PIT 快照选择

`_pit_snapshot()`先执行：

```python
(pit_date <= T) & (end_date < T)
```

再按 `end_date, pit_date`排序，使用 `drop_duplicates("ts_code", keep="last")`取整行。

这里不用 `groupby.last()`的原因是：pandas 的 `last()`可能对每一列分别跳过 NaN，拼出一行在原数据中从未存在过的“混合记录”。取排序后的整行更安全。

### 12.4 缓存风险

模块级缓存的隐含前提是处理文件在进程运行期间不会被替换。否则 loader 仍可能返回旧数据。重建数据后应调用 `clear_cache()`，更工业化的方案是缓存键包含数据版本或文件哈希。

## 13. 数据质量应该检查哪些维度

### 13.1 七类质量维度

| 维度 | 核心问题 | 本项目例子 |
|---|---|---|
| 完整性 Completeness | 必需字段和日期是否缺失 | `adj_factor`、`free_share`、行业覆盖 |
| 唯一性 Uniqueness | 主键是否重复 | `(trade_date, ts_code)`重复 |
| 有效性 Validity | 值是否满足定义和范围 | 价格非正、代码格式错误 |
| 一致性 Consistency | 公式和跨表字段是否一致 | 自由流通市值复算、两表 close 对齐 |
| 完整性 Integrity | join 是否丢行或膨胀 | 复权因子合并、财务三表合并 |
| 时效性 Timeliness | 数据是否覆盖目标期且及时 | 最新分区、ST历史、行业历史 |
| 时间正确性 PIT | T 日是否只用当时可见信息 | 财报公告日、成分生效日 |

### 13.2 必须分段检查

只报告全样本平均空值率是不够的。至少按以下维度分解：

```text
年份 / 月份
股票 / 行业
数据源文件
训练 / 验证 / 测试边界
新上市 / 退市 / 特殊状态
```

项目的行业问题就是典型例子：全样本覆盖率能通过，但 2012～2013 年约三分之一股票未分类。

### 13.3 转换前、中、后都要有门禁

```text
转换前：原始文件清单、schema、覆盖区间、下载状态、checksum
转换中：类型转换失败数、join 行数变化、去重数量、冲突版本数
转换后：主键、日期、空值、公式、跨表覆盖、PIT、分段分布
发布前：临时产物复读、质量报告、哈希、原子替换
```

### 14.1 已有能力

`scripts/build_data_quality_notebook.py`会生成 `notebooks/01_processed_data_quality_report.ipynb`，其中包含：

- 跨表日度覆盖率。

这比只看 `describe()`强很多，值得保留。

### 14.2 当前缺口

1. `run_pipeline.py`中的 `quality`仍是占位；必须使用 `--skip quality`才能继续。
2. notebook 主要是交互式诊断，不是可重复、返回非零退出码的生产门禁。
3. `ret == pct_chg/100`是错误契约，与后复权收益定义冲突。
4. 阈值没有集中配置，也没有 schema version。
5. 质量结果没有和输入哈希、处理代码版本、输出哈希绑定。
6. 转换核心函数缺少直接单元测试。
7. 全局描述仍可能掩盖按月、按行业和按股票的局部缺口。

### 14.3 推荐的最小质量门禁程序

未来应实现 `scripts/run_data_quality.py`，至少：

```text
输入：processed 目录 + 数据版本 manifest + 允许的研究日期上限
输出：machine-readable JSON + 人类可读 Markdown
退出码：ERROR 时非零；只有全部 required checks 通过才为 0
```

核心规则应分成：

- `ERROR`：阻断下游；
- `WARN`：需有批准的例外说明；
- `INFO`：描述性统计。

## 16. 业界级目标架构

```text
供应商 API
  ↓ 原响应 + request metadata
Raw immutable snapshot
  ↓ schema contract / source manifest
Staging conversion
  ↓ 类型、单位、主键、PIT、区间连接
Temporary Parquet version
  ↓ automated quality gate
Quality report + lineage + checksums
  ↓ only if PASS
Atomic publish / version pointer switch
  ↓
Version-aware loader
  ↓
因子构建（只读取获准版本）
```

一份理想 manifest 至少包含：

```yaml
dataset: daily_quote
schema_version: 1
source: tushare.daily + tushare.adj_factor
requested_start: 2011-01-01
requested_end: 2022-12-31
actual_min_date: 2011-01-04
actual_max_date: 2022-12-30
row_count: 3560130
primary_key: [trade_date, ts_code]
source_checksums: {...}
output_checksum: ...
code_commit: ...
quality_status: PASS
published_at: ...
```

注意：上面的日期和行数是本轮训练/验证范围只读抽查所见，用来展示结构，不应被硬编码成永久阈值。

## 18. 面试高频问答

### Q1：数据清洗和数据质量有什么区别？

清洗是改变数据，例如解析日期、统一类型、去重和单位换算；质量验证是判断改变后的数据是否满足契约。清洗不能证明结果正确，质量验证也不应悄悄修改数据。

### Q2：如何定义重复数据？

先定义粒度和主键。日行情按 `(trade_date, ts_code)`；财务版本按 `(pit_date, ts_code, end_date)`；事件表可能还需要 `event_id`。没有粒度就不能正确谈去重。

### Q3：重复记录直接 `drop_duplicates()`可以吗？

不能一概而论。完全相同的重复可以去掉；同键不同值属于冲突，必须根据更新时间、修订标志或供应商版本规则选择，并记录冲突数。无法解释时应阻断。

### Q4：缺失值一般怎样处理？

先判断缺失语义：没有事件、尚未披露、下载失败、停牌、字段不适用是不同状态。价格不随意插值，财务不使用未来值回填，横截面因子可在后续预处理阶段基于明确规则处理，但原始标准层保留缺失及原因。

### Q5：为什么财务数据必须 PIT？

报告期说明数据描述什么时候，不说明市场什么时候知道。回测必须按公告可用日过滤，否则会把未来披露值放回历史。

### Q6：如何处理财报修订？

保存每个可见版本；T 日先筛选 `pit_date <= T`，再对每个报告期取当时最新版本，最后选择所需报告期或计算 TTM。不能让最终修订覆盖历史。

### Q7：为什么用 Parquet 而不是 CSV？

Parquet 是列式、有类型、有压缩、支持列裁剪和谓词下推，适合反复读取大规模研究数据；CSV 更适合作为简单、可观察的原始交换格式，但类型和读取性能较弱。

### Q8：Parquet 会自动保证数据正确吗？

不会。它只解决存储格式和读取效率，不保证主键、PIT、单位、覆盖率或业务规则。

### Q9：如何发现 join 造成的数据膨胀？

合并前检查双方键唯一性，使用 pandas `validate="one_to_one"`或`many_to_one`，记录合并前后行数、未匹配率和重复键样本。行数意外增加通常说明右表不是预期粒度。

### Q10：如何做跨表一致性检查？

比较共享键覆盖率和同义字段。例如 `daily_basic.close`与`daily_quote.close`、成分股调仓日是否存在行情、状态表是否覆盖成分股、自由流通市值是否能由原始字段复算。

### Q11：为什么不能只看总体缺失率？

总体平均会掩盖局部故障。应按日期、股票、行业和数据源分段；本项目行业全局能过，但 2012～2013 年约三分之一未分类。

### Q12：异常值怎样处理？

标准层先识别和保留审计信息，不根据模型表现随意删值。价格和数量先用硬业务规则；分布异常优先用分位数、MAD/IQR诊断。因子去极值属于后续截面预处理，并且边界只能来自同一个 T 日截面。

### Q13：如何避免未来函数？

区分事件发生时间、报告期和实际可用时间；只做 backward as-of；禁止未来回填；保留修订版本；对成分、行业和状态使用历史快照；写时间边界单测和人工样本。

### Q14：为什么不能用当前指数成分股回测历史？

会产生幸存者偏差。今天仍在指数里的股票通常是历史上存活和表现较好的公司，必须使用每个历史生效日的成分股快照。

### Q15：什么是数据泄漏和未来函数的区别？

未来函数是泄漏的一类，指使用决策时点之后的信息。更广义的数据泄漏还包括训练/验证统计量混用、用全样本做标准化、标签参与特征处理等。

### Q16：为什么验证要在写文件之前？

因为正式路径代表下游可消费版本。若先写后验，失败文件仍可能被后续任务读取。应在 staging 中验证，PASS 后原子发布。

### Q17：数据质量阈值怎样设？

优先使用稳定业务契约，如主键重复必须为0、指数代码必须唯一、PIT未来行必须为0。分布和覆盖阈值应依据历史基线、数据源语义和下游容忍度设定，不能凭经验随意写一个数。

### Q18：告警和阻断怎样区分？

会改变研究结论、造成未来函数、破坏主键或关键 join 的问题应阻断；可解释且下游可容忍的稀疏性可以告警，但必须有范围、原因和批准记录。

### Q19：怎样保证可复现？

固定代码版本、依赖版本、配置、原始快照、输入输出哈希和随机种子；中间产物落盘；每次运行生成 manifest；任何结果能追到数据版本和处理代码。

### Q20：这个项目的数据处理哪里做得最好，哪里最需要改？

做得较好的是后复权口径、自由流通市值单位、全收益基准、PIT版本保留和 loader 的时间过滤。最需要改的是自动 quality gate、先写后验、下载 manifest、历史行业/ST覆盖，以及财务三表交错修订合并。

## 19. 一道白板题：从原始数据得到 T 日可用截面

面试官给出行情、复权、财务和成分股四张表，可以按下面顺序回答：

1. 定义各表粒度与主键；
2. 校验日期、代码、类型和单位；
3. 行情与复权因子按股票日做 `many_to_one`左连接；
4. 由复权价格计算收益，不用未来价格填缺失；
5. 取 T 日正式生效的指数成分股；
6. 财务表过滤 `pit_date <= T`；
7. 对同报告期取 T 日可见的最后修订；
8. 取最新合格报告期或构造 TTM；
9. 连接 T 日自由流通市值、行业和状态；
10. 检查 join 覆盖率、行数变化、未分类和缺失；
11. 只有质量门禁通过才输出 T 日截面；
12. T 日盘后形成信号，T+1开盘执行。

这道题的重点不在 pandas 语法，而在你是否把时间、版本、粒度和可交易性说清楚。

## 21. 学习练习与自测

### 练习 1：复权收益

找一只发生分红送转的股票，手算连续两日：

```text
close_adj_t = close_t × adj_factor_t
ret_t = close_adj_t / close_adj_(t-1) - 1
```

再比较原始 `pct_chg`，解释为何可能不同。

### 练习 2：join 膨胀

构造行情表两行、复权表同键两行，观察普通 `merge`为何变成四行；再使用 `validate="many_to_one"`让错误立即暴露。

### 练习 3：财报修订

构造一份初版和一份修订版，分别在公告日前、初版后、修订后查询，写出每个 T 日应返回的值。

### 练习 4：行业区间

构造两个连续行业区间，检查 `out_date`当天属于旧行业还是新行业，并解释项目采用半开区间的原因。

### 练习 5：质量门禁

设计以下五个故障并判断 ERROR/WARN：

- 日行情主键重复；
- 某稀疏事件文件合法为空；
- 2012年行业缺失30%；
- 财务 `pit_date > T`；
- 最新一周数据因正常发布滞后不完整。
